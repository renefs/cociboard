# Review 0002 — v0.9.0 shopping list (planning/review model: Opus)

Scope: the v0.9.0 working tree written by the development subagent (Sonnet), before the
commit. Gates: `make check` passes (pytest 117, vitest 210 before the fixes below).

## Verified manually
- 1440px: Suggest fills the week, **Shopping list** opens a dialog with 54 merged items;
  "Aceite de oliva" shows ×14 with its recipes.
- Ticking two items moves them to "In the basket", and `GET .../shopping-list` returns
  them as checked. Adding "Leche" and "Pan" with Enter stores them as extras (ids 1, 2).
- 375px: full-screen sheet, no horizontal scroll, 24px checkboxes in ~60px rows, footer
  actions stay visible; the three toolbar buttons wrap onto two lines. Escape closes the
  dialog and focus returns to the toolbar button. No console errors.
- Share is hidden in the desktop browser (no `navigator.share`); not tried on a phone.

## Findings (fixed in this release)

### 1. Shopping changes were sent concurrently (medium)
`useShoppingActions` sent every change at once. Ticking and unticking an item quickly
could reach the server in reverse order, leaving it checked while the UI showed it
unchecked until the refetch. This is the race review 0001 fixed for plan changes.

**Fix:** the mutation uses a TanStack Query `scope` per week, so the changes of one week
are sent one at a time, in order. Optimistic updates stay immediate.

### 2. Pending extras shared the id -1 (low)
Two items added before the first answer came back both had id `-1`, so they had the same
React key and could render wrongly. **Fix:** every pending extra gets its own negative id
(`isPendingExtraId`), with a unit test.

### 3. `React.ReactNode` without an import (low)
`ShoppingListDialog.tsx` used the global `React` namespace. It now imports `ReactNode`.

## Accepted as-is
- `_planned_meals` loads each recipe separately (at most 14 queries per week), as accepted
  for `_load_recipes` in review 0001.
- Staples such as oil or garlic list many recipes and take up a lot of room. A "pantry
  staples" setting is recorded as future work in ADR-0012.
- Ticks for ingredients that left the plan stay in the database. They are invisible and
  apply again if the ingredient comes back that week.
- No Planner-level test for the toolbar button or for the query invalidations; they are
  small and were checked in the browser.
