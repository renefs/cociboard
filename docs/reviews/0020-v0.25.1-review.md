# Review 0020 — v0.25.1 keyboard pick-up fix (model: Opus)

Scope: the fix for the follow-up recorded in review 0019 ("when a keyboard drag starts from a
filled slot, dnd-kit's first announcement can name a neighbouring slot"). Gates:
- `make check` passes.
- `make e2e` passes (56 tests).
- `npx playwright test e2e/keyboard.desktop.spec.ts --project=desktop --repeat-each 15`
  passes (60 tests).

## Cause
- `Slot` disabled the dragged meal's own droppable (`disabled: dragBlocked || isOwnSlot`).
- A keyboard drag has no pointer, so `collisionDetection` falls back to `closestCenter` over
  the *enabled* droppables, measured from the meal's own rect. With its own slot left out, the
  closest one is a neighbour: dnd-kit announced "over Tuesday dinner" and an immediate Space
  dropped the meal there. Arrow keys were fine because `keyboardCoordinates` moves the rect
  onto the chosen slot first.
- The own slot's `a11y.overOwn` sentence existed but was only reachable during the render race
  before the droppable was disabled, which is why the first announcement varied.

## Fix
- New pure rule `acceptsDrop(plan, source, target)` in `dragLogic.ts`: enabled when nothing is
  dragged, when `canDrop` allows the drop, and for the source's own slot. `Slot` uses it for
  `disabled`. Dropping on the own slot already resolves to no action, so the drop announces
  "was not moved". The own slot gets no `slot--over` or `slot--drop-ok` style (both still need
  `canDrop`), and pointer drags over it behave as before (no action).
- Side effect, intended: arrow keys can now bring the meal back over its own slot, and pointer
  hovering it announces "is over its own slot" instead of "no longer over a drop target".

## Tests
- Vitest (`dragLogic.test.ts`): `acceptsDrop` cases, and a pick-up scenario that runs the real
  `collisionDetection` with no pointer and the meal's rect on Wednesday dinner, using
  `acceptsDrop` to choose the enabled droppables. It expects the own slot first and a
  "not moved" drop. With the own-slot rule removed, the three new tests fail.
- E2E (`keyboard.desktop.spec.ts`): the workaround regex (`/^Baked salmon is over \w+
  dinner\.$/`) is replaced by the exact own-slot sentence, and a new test picks a meal up and
  drops it at once. It checks the "not moved" announcement and that the meal and its
  neighbours are unchanged. With the old `disabled` it fails with "Baked salmon was moved to
  Tuesday dinner."

## Found while testing
- dnd-kit's `KeyboardSensor` adds its keydown listener in a `setTimeout` after the pick-up,
  and the announcement can render first. Playwright pressed Space about 4 ms later, before the
  listener existed. The browser then turned that key into a click on the focused meal button,
  which opened the slot actions dialog. A person cannot press that fast. `pickUpWithKeyboard`
  now waits for a timer queued after the announcement, which runs after dnd-kit's. This is
  also the likely reason for the "first arrow press doesn't always move it" note in
  `pressUntilAnnounced`; that helper was left as it is.

## Accepted as-is / follow-ups
- Verified with Playwright in Chromium at 1440px only (the keyboard spec is desktop-only). The
  change does not affect touch, where drags use the pointer and `pointerWithin`.
