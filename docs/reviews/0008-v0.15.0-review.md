# Review 0008 — v0.15.0 optional household password (planning/review model: Opus)

Scope: the v0.15.0 working tree written by the development subagent (Sonnet), before the
commit. Gates: `make check` passes (279 pytest, 341 vitest, ruff, mypy --strict, tsc,
ESLint).

## Security review
- Hashing: stdlib scrypt (n=2^15, r=8, p=1, 16-byte salt), encoded without `$` so compose
  `.env` files don't interpolate it. Verification uses `hmac.compare_digest` and runs in a
  worker thread. A malformed `COCIBOARD_PASSWORD_HASH` stops the start-up with a clear error.
- Sessions: `v1.<issued>.<HMAC-SHA256>` bound to a fingerprint of the password hash, so a
  new password ends every session. Expiry and future timestamps are rejected; renewal only
  through `GET /api/auth/status`.
- Cookie: HttpOnly, SameSite=Lax, Path=/, 90-day Max-Age, Secure when the request is
  https (including `X-Forwarded-Proto` through uvicorn's proxy headers).
- Every `/api` path except health and `auth/*` needs the session; the static SPA shell is
  public and holds no data. Unsafe methods with a foreign `Origin` get 403, login included.
- Secret key: `COCIBOARD_SECRET_KEY`, else `cociboard.secret` next to the database, created
  atomically with mode 0600 by the PUID user; `*.secret` is git-ignored.

## Verified manually
- Dev servers on 8765/5199 with `COCIBOARD_PASSWORD` and a throwaway database:
  - 1440px: the login screen appears, a wrong password shows the error, the right one
    opens the planner with "Salir" in the header.
  - Logging out behind the app's back, then changing week, returns to the login screen.
  - 375px: login screen with 44px targets and no horizontal scroll; after the fix below
    the planner header fits too.
  - curl: `/api/recipes` 401 without a cookie, `/api/health` 200, cookie flags as above
    (Secure with `X-Forwarded-Proto: https`), `Origin: https://evil.example` 403.
- Podman image built from the working tree: the hash made with
  `python -m cociboard.auth hash` inside the image has no `$`; with PUID 1026 the API
  answers 401, login 204, the session still works after `podman restart` (persisted
  `cociboard.secret`, mode 0600), and the frontend answers 200.

## Findings (fixed in this release)

### 1. Concurrent logins could bypass the rate limit (medium)
The limit was checked before the password and the failure recorded after it (plus a 1 s
delay), so a burst of parallel attempts all passed the check. **Fix:**
`LoginRateLimiter.acquire()` checks and counts the attempt atomically before the password
is verified; a successful login resets that IP. Covered by a test.

### 2. Header overflowed 375px with the logout button (low)
Backup, logout and the language switcher made the header 397px wide. **Fix:** below 420px
the header uses tighter gaps and padding and a smaller title; all targets stay 44×44px.

### 3. Short `COCIBOARD_SECRET_KEY` accepted silently (low)
Now logs a warning when it is shorter than 32 characters.

## Accepted as-is
- The global cap (100 failures / 15 min) lets anyone who can reach the app block new logins
  for up to 15 minutes; existing sessions keep working. It is the price of not trusting
  `X-Forwarded-For` (uvicorn runs with `--forwarded-allow-ips "*"`). ADR-0018 notes it.
- With a plain `COCIBOARD_PASSWORD` the salt is derived from the secret key so sessions
  survive restarts; whoever can read the key file can also read the database.
- The exposure warning relies on the client address; behind NAT or rootless port
  forwarding a public client can look private, so it can miss cases (never a false alarm
  on a LAN).
- The exposure banner was only checked in component tests, not in a browser (it needs a
  public client address).
